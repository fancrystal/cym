# 本地商圈独立系统设计方案

日期：2026-11-07  
状态：基于已确认需求的设计，供实施和验收使用。

## 1. 目标与边界

在 `D:\work\cym` 建立独立的本地商圈系统，参考 `D:\work\mskj\backups\project\mskj` 的现有页面和商圈行为。仅提供移动 H5、运营管理后台和 API；H5 与后台均需适配手机窄屏。界面延续现有清爽卡片风格，适当简化。

使用全新数据库，不导入历史用户、关系、资产、商品和订单。产品数据和图片通过后台重新录入或按需从源项目选取。删除普通商城、PC 用户端、聊天室、私信、语音、通证、权益值、贡献值、代理、VIP 及其逻辑，不保留隐藏的旧 API。

## 2. 已核对的源项目行为

- 商圈注册使用 `transfer_invite_code`，建立独立 `transfer_relationships`；不能用根账户邀请码注册。
- H5 原“我的二维码”使用的是旧体系的 `invite_code`；商圈中心仅复制商圈邀请码。新系统需生成商圈专用二维码和链接，不能直接沿用旧二维码。
- 商圈购买每次一件，使用产品券、库存和收货地址，可配置商品款式；购买事务同时处理订单、库存、次数、收益及流水，按用户和请求 ID 防重。
- 第 N 次购买对应第 N 层上级，上级购买次数至少为 N 才取得固定收益，否则由系统根账户承接；关系缺失也归根账户。根账户不可购买、邀请或作为普通上级。
- 源商圈购买接口创建订单时直接设为 `completed`；到货通知和后台订单功能有独立状态判断。应按实际代码和现有测试复刻可用行为，联调确认通知入口与状态兼容，不自行改造为新的发货状态机。
- 源产品券转赠需要权益值，且金额为大于等于 1 的整数。新系统保留整数转赠、密码验证和原额到账，删除权益值校验和扣除；有足额余额方可转赠。
- 原后台订单页已有窄屏卡片，但商圈明细仍主要为横向表格，需要针对手机优化。

## 3. 用户功能

1. 手机号、密码登录；通过商圈邀请码注册，支持用户名及源项目所需的基础资料；修改密码和用户名。
2. 商圈首页展示商品、购买价格、固定收益、库存、复购次数和累计收益；展示团队总人数及分组人数。
3. 商品详情、图片、款式选择、地址选择与购买；余额、库存、地址或身份不满足时显示明确提示。
4. 商品管理由后台控制；H5 支持订单列表、订单详情、到货通知和源系统可用的订单操作。
5. 管理收货地址；查看产品券余额、充值、购买、收益和转赠流水；通过手机号和登录密码转赠产品券。
6. 显示、复制商圈邀请码和邀请链接，生成可保存或展示的二维码。二维码指向 `https://cym.green/#/login?transfer_invite=<邀请码>`，打开后进入商圈注册并预填邀请码；手动输入走同一接口。二维码由外部扫码工具识别，不依赖原 Android 桥。

## 4. 后台功能

- 管理员登录及权限控制；用户查询、状态管理、产品券充值和流水。
- 商圈商品增删改查、上架下架、库存、商品图片与详情、款式、消耗和固定收益配置。删除应避免破坏已有订单，优先采用停用或受约束删除。
- 商圈订单搜索、详情、源系统允许的订单操作与到货通知。
- 商圈运营看板：成交数量、产品券消耗和收益、趋势、商品排行、复购序号和收益去向；统计口径参照原商圈后台。
- 根账户初始化，不开放普通邀请或购买功能。首批普通用户由运营方直接写入数据库；提供字段、密码哈希和邀请码生成说明及校验脚本，不自动导入历史数据。

## 5. 数据与结算

使用独立 MySQL 数据库与专用账号。设计用户、管理员、商品、地址、订单、到货通知、产品券流水、商圈关系、购买次数、商圈订单和收益记录；仅保留本项目所需字段。金额使用数据库 DECIMAL（两位小数），不得用浮点计算余额；转赠数量限制为整数，购买金额允许两位小数。

购买事务锁定相关用户、商品和计数，验证库存、余额、地址、商品与根账户；原子写入扣款、库存、次数、订单、收益和双方流水。对请求 ID 建唯一约束并在重试时返回原结果；死锁重试有上限。转赠验证密码、禁止转给自己、锁定双方账户，原子记账并保留双方流水；重复提交采用请求 ID 防重。后台充值同样写入操作人和流水。

初始化独立商圈根账户，手机号为 `18801620766`，密码采用用户已提供的初始值，运行初始化时安全输入并以 bcrypt 哈希存储，不写进仓库、示例环境变量或日志。管理员账户与商圈根账户为不同身份；管理员初始化凭据通过部署时安全输入设置。首批普通账户应有有效唯一邀请码及登录凭据，关系、余额按初始化说明设置。

## 6. 界面与窄屏适配

H5 保留源项目商圈商品卡片、蓝色重点色、简洁底部导航，移除旧资产、聊天室及代理入口。用户主要路径为登录/注册、商圈、订单、我的；小屏下信息分组，按钮与表单可触达，长内容自然换行。

后台保留现有绿色运营风格，导航仅包含商圈业务。桌面可使用侧栏和表格；窄屏使用抽屉导航、筛选项纵向排列、订单和用户数据卡片或受控横向滚动。弹窗在手机视口内滚动，提交和关闭按钮可见。以 320、375、390 和 768 像素宽及桌面视口验收，检查键盘弹出、长手机号、长订单号、表单错误和加载状态。

## 7. 架构与同服务器部署

- Node.js 20+、pnpm workspace、Express、MySQL 8+；H5 和后台沿用 Vue 3 + Vite。仅在确有需要时引入 Redis，不引入聊天、语音依赖。
- `cym.green` 提供 H5；`admin.cym.green` 提供后台。两个 Nginx 独立虚拟主机分别提供对应静态构建，并将 `/api/` 反向代理至同一个仅监听本机的独立 API 服务；各域名使用同源 API 路径。
- 独立部署目录、服务名称、环境文件、日志、数据库、数据库账号和上传目录。端口只在目标服务器检查已有监听后选定，不能假定原系统端口可用。Nginx 配置按域名精确匹配，不修改或覆盖 mskj 现有站点。
- 为两个域名配置 DNS 与 HTTPS 证书；DNS、证书、Nginx 目录、现有进程管理方式和服务器权限须在实际部署前核实，当前尚未连接服务器验证。配置上传文件大小限制、日志轮转、健康检查与备份恢复。
- 上线前备份现有配置，测试 Nginx 配置及新服务健康状态；上线后分别验证两个域名、静态资源、API 和 mskj 原站点。失败时回滚新站点配置和新服务，不改动原站数据库。

## 8. 分阶段实施

1. **项目基础**：梳理源代码和测试依赖，建立 H5、后台、API workspace、独立数据库迁移、环境示例及本地运行文档。
2. **身份与邀请**：管理员和用户登录、首批用户说明、根账户、安全密码存储、商圈邀请码及二维码注册。
3. **产品券与结算**：充值、流水、整数原额转赠；迁移商圈商品、地址、购买和收益事务及幂等控制。
4. **H5**：迁移并简化商圈、详情、团队、订单、地址、个人中心；移除所有旧体系入口。
5. **后台**：迁移用户、商品、订单、到货通知和商圈报表，完成窄屏适配。
6. **验证与部署准备**：运行后端业务测试和两端构建，完成真实 MySQL 联调、手机视口验收、初始化和备份恢复演练，准备独立部署配置。

## 9. 验收标准

- 空数据库初始化后，根账户可登录但不可邀请或购买；首批普通用户可按说明建立，二维码与邀请码均绑定正确的商圈上级。
- 从充值到购买、复购收益、转赠、订单和后台统计能逐笔对账；金额和库存准确，并发及重复请求不重复扣款、发奖或转赠。关系缺失、资格不足正确归根账户。
- 余额不足、商品下架或缺货、无有效地址、密码错误、自转、停用用户及越权请求均被拒绝，失败不留下部分账目。
- H5 和后台在指定窄屏尺寸均可完成核心操作；商圈报表和订单信息完整可读。
- 不提供被排除功能的页面、接口或依赖；新库无旧历史数据。
- 两个域名通过 HTTPS 访问各自页面及 API；重启、备份恢复可验证；原 mskj 站点运行不受影响。

服务器系统、现有 Nginx 和进程管理方式、端口、DNS、证书与文件上传存储尚未实测；部署阶段先只读检查，再以实际环境生成配置。用户尚未要求发布，本设计不包含对服务器执行操作的授权。
